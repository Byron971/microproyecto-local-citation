\section{Resumen del problema}

La producción de literatura científica crece continuamente y hace cada vez
más difícil que un investigador identifique rápidamente qué trabajo debe
citar para respaldar una afirmación específica.

La recomendación local de citas aborda este problema usando como consulta
el fragmento textual próximo al lugar donde se requiere incluir una
referencia. A partir de este contexto, el sistema busca y ordena los
artículos que podrían ser relevantes para la afirmación realizada.

\notabox{
\textbf{Pregunta de negocio:}
¿Cómo apoyar a un autor de textos académicos en la identificación de
artículos potencialmente relevantes para citar utilizando el contexto
textual local en el que requiere incluir una referencia?
}

El resultado esperado es un prototipo que recibe un contexto académico en
inglés y devuelve un ranking de artículos candidatos, permitiendo consultar
sus títulos, identificadores, resúmenes y puntajes de relevancia desde una
interfaz web.

\section{Conjunto de datos}

El proyecto utiliza el conjunto \texttt{custom} (ACL-200) proveniente del
repositorio \textit{Local-Citation-Recommendation}.

El conjunto empleado contiene:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item 63.768 contextos de cita.
    \item 19.776 artículos candidatos.
    \item 30.390 consultas de entrenamiento.
    \item 9.381 consultas de validación.
    \item 9.585 consultas de prueba.
\end{itemize}

Los artículos contienen título y resumen, mientras las consultas representan
fragmentos de texto académico asociados con la referencia que fue utilizada
en el documento original.

Los datos no son almacenados directamente en Git debido a su tamaño.
El versionamiento se realiza mediante DVC utilizando
\texttt{data/raw.dvc} y \texttt{data/processed.dvc}.

De esta manera se mantiene separado el control de versiones del código y
el control de versiones de los datos, conservando la trazabilidad necesaria
para reproducir los experimentos.

% 3. ARQUITECTURA
% ============================================================================

\section{Arquitectura desarrollada}

La solución utiliza una arquitectura de recuperación y reordenamiento en
dos etapas.

\subsection{Primera etapa: recuperación TF--IDF}

El contexto de cita se representa mediante TF--IDF y se compara contra los
19.776 artículos del corpus mediante similitud coseno.

La primera etapa selecciona los 100 candidatos con mayor similitud.

\subsection{Segunda etapa: reordenador supervisado}

Los 100 candidatos son posteriormente evaluados mediante una regresión
logística que aprende a distinguir entre artículos relevantes y no
relevantes.

El modelo utiliza cinco características:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item similitud TF--IDF contexto--título;
    \item similitud TF--IDF contexto--resumen;
    \item longitud del contexto;
    \item longitud del título;
    \item longitud del resumen.
\end{itemize}

El flujo completo puede resumirse como:

\begin{center}
\small
Contexto
$\rightarrow$
TF--IDF
$\rightarrow$
Top--100
$\rightarrow$
Regresión logística
$\rightarrow$
Top--K
$\rightarrow$
API
$\rightarrow$
Tablero
\end{center}

Esta arquitectura evita aplicar el reordenador supervisado a los 19.776
artículos para cada consulta y permite conservar tiempos de respuesta
compatibles con un prototipo interactivo.

\section{Entrenamiento del modelo supervisado}

El modelo supervisado se entrenó empleando una consulta positiva y dos
ejemplos negativos por consulta.

Con las 30.390 consultas de entrenamiento se construyeron aproximadamente
91.170 pares contexto--artículo.

Se analizaron dos estrategias diferentes para seleccionar los negativos.

\subsection{Negativos aleatorios}

La estrategia \texttt{random} selecciona artículos incorrectos de manera
aleatoria dentro del catálogo.

Esta estrategia representa ejemplos relativamente sencillos, pero permite
al modelo aprender una frontera estable entre positivos y negativos.

La Figura~\ref{fig:train-random} presenta la ejecución del entrenamiento
realizada desde el repositorio.

\begin{figure}[H]
\centering
\includegraphics[width=0.88\textwidth]{entrenamiento_random_terminal.png}
\caption{Ejecución del entrenamiento de la variante con negativos aleatorios.}
\label{fig:train-random}
\end{figure}

\subsection{Negativos difíciles}

La estrategia \texttt{hard} selecciona como negativos artículos incorrectos
que aparecen entre los primeros candidatos recuperados mediante TF--IDF.

Estos ejemplos son considerablemente más parecidos léxicamente al contexto.

La Figura~\ref{fig:train-hard} muestra la ejecución de esta segunda variante.

\section{Comparación de los modelos}

Las variantes se evaluaron utilizando las mismas consultas de validación,
la misma semilla, los mismos 100 candidatos recuperados y los mismos
hiperparámetros.

Las métricas principales fueron Recall@K y MRR@K.

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item \textbf{Recall@K}: mide si el artículo correcto se encuentra entre
    las primeras $K$ posiciones.
    \item \textbf{MRR@K}: considera además qué tan arriba aparece el primer
    resultado correcto.
\end{itemize}

Los principales resultados se presentan en la
Tabla~\ref{tab:resultados}.

\begin{table}[H]
\centering
\small
\caption{Resultados de las estrategias Random y Hard}
\label{tab:resultados}

\begin{tabular}{lccc}
\toprule
\textbf{Modelo} &
\textbf{Recall@10} &
\textbf{MRR@10} &
\textbf{Recall@100} \\
\midrule

Regresión logística -- Random &
\textbf{0,2882} &
\textbf{0,1490} &
0,5160 \\

Regresión logística -- Hard &
0,0629 &
0,0212 &
0,5160 \\

\bottomrule
\end{tabular}
\end{table}

La estrategia Random presenta un desempeño claramente superior en las
primeras posiciones del ranking.

Recall@10 aumenta de 0,0629 a 0,2882 y MRR@10 aumenta de 0,0212 a
0,1490.

Las Figuras~\ref{fig:recall-comparison} y
\ref{fig:mrr-comparison} muestran gráficamente esta diferencia.

\begin{figure}[H]
\centering
\includegraphics[width=0.72\textwidth]{comparacion_random_hard_recall10.png}
\caption{Comparación de Recall@10 entre negativos aleatorios y difíciles.}
\label{fig:recall-comparison}
\end{figure}

\begin{figure}[H]
\centering
\includegraphics[width=0.72\textwidth]{comparacion_random_hard_mrr10.png}
\caption{Comparación de MRR@10 entre negativos aleatorios y difíciles.}
\label{fig:mrr-comparison}
\end{figure}

El hecho de que Recall@100 permanezca aproximadamente en 0,516 para ambas
variantes demuestra que los modelos reciben el mismo conjunto de candidatos.
La diferencia observada se produce por la manera en la que cada reordenador
organiza esos candidatos.

El experimento con negativos difíciles muestra además que utilizar ejemplos
más difíciles no garantiza automáticamente un mejor modelo. Los candidatos
difíciles presentan alta similitud léxica con el contexto y el conjunto
actual de cinco características no contiene suficiente información
semántica para distinguirlos adecuadamente.

Como resultado de esta comparación se seleccionó la estrategia
\texttt{random} para el modelo empaquetado.

La configuración seleccionada actualmente en
\texttt{config/model.yaml} corresponde a:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item semilla: 42;
    \item estrategia de negativos: random;
    \item negativos por positivo: 2;
    \item Top--N: 100;
    \item $K$: 10;
    \item \texttt{max\_features}: 50.000;
    \item \texttt{min\_df}: 2;
    \item $C$: 1,0.
\end{itemize}

\section{Infraestructura de MLflow en AWS}

Para compartir los experimentos entre integrantes se desplegó un servidor
MLflow sobre una instancia EC2 de AWS Academy.

El servidor utiliza:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item Ubuntu Server 24.04 LTS;
    \item MLflow 3.15.1;
    \item SQLite como backend de metadatos;
    \item almacenamiento local de artefactos;
    \item puerto TCP 8050;
    \item un proceso worker para mantener estabilidad dentro de los recursos
    disponibles en la instancia.
\end{itemize}

El servicio de MLflow quedó configurado mediante \texttt{systemd}, lo cual
permite iniciarlo automáticamente cada vez que la instancia se reinicia.

La Figura~\ref{fig:mlflow-service} muestra la evidencia del servicio
funcionando en la instancia.

\begin{figure}[H]
\centering

\caption{Servicio MLflow activo y administrado mediante systemd en la instancia EC2.}

\subsection{Conexión automática desde el entorno local}

AWS Academy utiliza credenciales temporales y la dirección pública de una
instancia puede cambiar después de detenerla e iniciarla.

Para evitar actualizar manualmente la dirección del servidor dentro del
proyecto se desarrolló el script:

\begin{center}
\texttt{scripts/conectar\_mlflow\_aws.ps1}

El script consulta AWS mediante CLI, obtiene la IP pública actual de la
instancia EC2, configura la variable:

\begin{center}
\texttt{MLFLOW\_TRACKING\_URI}
\end{center}

y finalmente verifica si el puerto 8050 está disponible.

La Figura~\ref{fig:mlflow-auto} evidencia este procedimiento funcionando.

\section{Empaquetamiento del modelo}

Uno de los objetivos principales de esta etapa fue separar el modelo de
inferencia del código de experimentación.

Para ello se creó el módulo:

\begin{center}
\texttt{model-package/}
\end{center}

que transforma el recomendador en una librería Python instalable denominada:

\begin{center}
\texttt{modelo-citas}
\end{center}

La versión validada actualmente es la 0.1.0.

El paquete incorpora:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item recuperador TF--IDF;
    \item reordenador lineal;
    \item configuración del modelo;
    \item modelo entrenado;
    \item metadatos de los artículos;
    \item función pública de inferencia.
\end{itemize}

El objetivo es que el consumidor del modelo no necesite importar
\texttt{src/}, descargar el dataset ni conocer el pipeline de entrenamiento.

La interfaz pública puede utilizarse de la siguiente forma:

\begin{verbatim}
from modelo_citas import make_prediction

resultado = make_prediction(
    context="Recent work on neural machine translation with attention",
    top_k=5,
)

print(resultado["predictions"])
\end{verbatim}

\subsection{Validación del wheel}

Durante la integración se realizaron las siguientes comprobaciones:

\begin{enumerate}[leftmargin=1.5em, itemsep=1pt]
    \item Entrenamiento del modelo desde el paquete.
    \item Ejecución de las pruebas específicas mediante Tox.
    \item Construcción del wheel.
    \item Instalación del wheel en un entorno virtual limpio.
    \item Importación de \texttt{modelo\_citas} desde
    \texttt{site-packages}.
    \item Ejecución de una predicción real desde el entorno limpio.
\end{enumerate}

Estas pruebas permiten demostrar que el wheel no funciona únicamente por
estar dentro del repositorio de desarrollo, sino como una dependencia
instalable independiente.

Posteriormente, el cambio fue revisado mediante Pull Request e integrado a
la rama principal.

Después de sincronizar nuevamente la rama de la Entrega 3 con
\texttt{main}, se ejecutó la suite completa:

\notabox{
\textbf{96 pruebas aprobadas.}

No se presentaron fallos funcionales después de integrar el paquete del
modelo con el resto del proyecto.
}

Las advertencias observadas corresponden principalmente a cambios deprecados
en NumPy/Joblib y se consideran deuda técnica no bloqueante.

\section{API del recomendador}

El modelo empaquetado fue integrado con un backend desarrollado mediante
FastAPI.

El backend carga el paquete \texttt{modelo-citas} durante el inicio de la
aplicación y permite realizar predicciones desde una interfaz HTTP.

Los principales endpoints son:

\begin{table}[H]
\centering
\small

\begin{tabular}{lll}
\toprule
\textbf{Método} & \textbf{Endpoint} & \textbf{Función} \\
\midrule
GET &
\texttt{/api/estado} &
Información del modelo cargado \\

POST &
\texttt{/api/recomendar} &
Generación de recomendaciones \\

GET &
\texttt{/api/insights} &
Información analítica para el tablero \\

GET &
\texttt{/api/ejemplo} &
Consulta real del corpus \\

GET &
\texttt{/docs} &
Documentación Swagger/OpenAPI \\

El endpoint \texttt{/api/recomendar} recibe un contexto y un número

Durante las pruebas manuales se verificó mediante Swagger que el endpoint
devuelve código HTTP 200 y recomendaciones reales.

El endpoint \texttt{/api/estado} reportó correctamente que el modelo servido
corresponde a:

\begin{center}
\texttt{TF-IDF + reordenador lineal}
\end{center}

con 19.776 artículos disponibles.

\section{Tablero desarrollado}

La aplicación web se encuentra en:

\begin{center}
\texttt{src/app/}
\end{center}

y se sirve desde el mismo proceso FastAPI.

El tablero puede ejecutarse localmente mediante:

\begin{center}
\texttt{uv run tablero}
\end{center}

y posteriormente abrirse en:

\begin{center}
\texttt{http://127.0.0.1:8000}
\end{center}

El componente principal permite:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item escribir un contexto académico en inglés;
    \item escoger la cantidad de resultados;
    \item solicitar recomendaciones;
    \item observar el ranking generado;
    \item revisar el resumen de un artículo seleccionado;
    \item cargar un ejemplo real conocido del corpus.
\end{itemize}

El tablero ya consume el modelo empaquetado TF--IDF más reordenador lineal
a través del backend.

También dispone de tres secciones analíticas:

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]
    \item Estudio de los datos.
    \item Desempeño del modelo.
    \item Diagnóstico de negativos.
\end{itemize}

Estas vistas integran en un único prototipo información que anteriormente
se encontraba distribuida entre notebooks, scripts de evaluación y
resultados experimentales.

\section{Manual de usuario}

El flujo básico para utilizar el tablero es el siguiente:

\begin{enumerate}[leftmargin=1.5em, itemsep=1pt]

    \item Abrir el tablero en el navegador.

    \item Escribir o pegar un fragmento académico en inglés dentro del campo
    \textit{Contexto de cita}.

    \item Seleccionar el número de artículos que se desean recuperar.

    \item Presionar \textit{Recomendar citas}.

    \item Revisar el ranking presentado en la zona
    \textit{Artículos recomendados}.

    \item Seleccionar uno de los resultados para visualizar su resumen.

    \item Para probar una consulta conocida, utilizar
    \textit{Usar un ejemplo real}.

    \item Consultar las pestañas inferiores para analizar datos, métricas
    y comportamiento de las estrategias de negativos.

\end{enumerate}

Los resultados constituyen recomendaciones y no reemplazan la revisión
académica del usuario. Antes de utilizar una referencia debe verificarse que
el contenido del artículo realmente respalde la afirmación realizada.

\section{Manual de instalación}

El proyecto utiliza \texttt{uv} para administrar el entorno Python y sus
dependencias.

El flujo principal de instalación es:

\begin{verbatim}
git clone https://github.com/Byron971/microproyecto-local-citation.git
cd microproyecto-local-citation

uv sync
uv run dvc pull

uv run pytest

uv run tox -c model-package -e train
uv sync --reinstall-package modelo-citas

uv run tablero
\end{verbatim}

Después de iniciar la aplicación se puede acceder al tablero en:

\begin{center}
\texttt{http://127.0.0.1:8000}
\end{center}

y a la documentación interactiva de FastAPI en:

\begin{center}
\texttt{http://127.0.0.1:8000/docs}
\end{center}

Si el remoto DVC no estuviera disponible, los archivos originales del
conjunto \texttt{custom} pueden recuperarse desde el repositorio público
\textit{Local-Citation-Recommendation}.

\section{Versionamiento y reproducibilidad}

La solución utiliza diferentes herramientas para controlar cada elemento
del ciclo de desarrollo.

\begin{itemize}[leftmargin=1.5em, itemsep=1pt]

    \item \textbf{Git/GitHub}: código, configuración, documentación y
    colaboración.

    \item \textbf{DVC}: versiones de los datos.

    \item \textbf{MLflow}: parámetros, resultados, métricas y artefactos de
    los experimentos.

    \item \textbf{uv}: resolución reproducible del entorno Python.

    \item \textbf{Tox}: validación del paquete dentro de entornos aislados.

    \item \textbf{pytest}: pruebas automatizadas del proyecto.

\end{itemize}

La configuración final seleccionada permanece explícita dentro de
\texttt{config/model.yaml} y utiliza una semilla fija de 42.

El modelo empaquetado mantiene además su versión dentro de:

\begin{center}
\texttt{model-package/modelo\_citas/VERSION}
\end{center}

Esta separación permite mantener trazabilidad entre el código experimental,
el modelo seleccionado y la versión distribuida para inferencia.

\section{Conclusiones}

Los resultados obtenidos muestran que el reordenamiento supervisado puede
mejorar el ranking generado por TF--IDF cuando se utiliza una estrategia
adecuada de construcción de pares de entrenamiento.

La variante con negativos aleatorios obtuvo Recall@10 de 0,2882 y MRR@10
de 0,1490, claramente superiores a los valores obtenidos por la variante de
negativos difíciles.

La igualdad aproximada de Recall@100 entre ambas configuraciones confirma
que el principal efecto del modelo supervisado ocurre sobre el orden y no
sobre la recuperación de candidatos.

El comportamiento de los negativos difíciles muestra una limitación del
modelo actual: la similitud léxica no ofrece suficiente información para
separar artículos temáticamente muy cercanos cuando se utilizan solamente
cinco características.

Desde el punto de vista de ingeniería, el proyecto también evolucionó desde
un conjunto de scripts experimentales hacia una solución reutilizable.
El modelo puede empaquetarse como un wheel, instalarse de manera independiente
y ser consumido directamente por la API y el tablero.

El seguimiento mediante MLflow permite mantener trazabilidad de las
ejecuciones, mientras Git, DVC, uv, pytest y Tox soportan la reproducibilidad
del código, los datos, las dependencias y las pruebas.

El siguiente paso del proyecto es completar la contenerización y el
despliegue reproducible de la API y el tablero, incorporar sus evidencias al
repositorio y cerrar los demás soportes requeridos para la Entrega 3.
